PROJECT NAME: FOOTBALL TOURNAMENT MANAGEMENT SYSTEM

Build a complete, production-ready Football Tournament Management Website with a public frontend and a secure admin dashboard.

IMPORTANT:
This must be a fully functional application, not a static design or prototype. All buttons, forms, tables, navigation, match controls, and administrative features must work and be connected to the backend and MongoDB database.

Do not use localStorage as the primary database. All permanent application data must be stored in MongoDB.

==================================================
1. PROJECT OBJECTIVE
==================================================

Create a modern football tournament management platform where administrators can create tournaments, register teams, schedule matches, update live scores, manage tournament stages, calculate league standings, and progress competitions through multiple stages until a champion is determined.

The public frontend must display tournament information, standings, fixtures, results, live matches, registered teams, and knockout brackets.

The administrator must manage everything through a secure dashboard without editing code or directly accessing the database.

The public frontend and admin dashboard must belong to the same website.

Example routes:

/                  Public tournament homepage
/tournament/:slug  Tournament details
/standings         Tournament standings
/fixtures          Upcoming fixtures
/results           Completed matches
/live              Live matches
/teams             Registered teams
/bracket           Knockout bracket
/match/:id         Individual match details
/admin/login       Administrator login
/admin             Admin dashboard
/admin/tournaments Tournament management
/admin/teams       Team management
/admin/stages      Tournament stage management
/admin/matches     Fixture and match management
/admin/settings    Application settings

Routes can be improved where necessary, but all functionality must be implemented.

3. MONGODB DATABASE CONFIGURATION
==================================================

Use MongoDB Atlas for persistent storage.

Read the database connection string from an environment variable:

MONGODB_URI

Use a configurable database name through:

MONGODB_DB_NAME

If a database name is not specified, use a sensible default.

Create a secure configuration system for environment variables.

Provide an .env.example file containing variable names and placeholder values only.

Never commit actual secrets to source control.

The server must:
- Connect to MongoDB during startup.
- Handle database connection failures gracefully.
- Avoid accepting requests that require the database before initialization completes.
- Close database connections cleanly during shutdown.
- Log useful operational errors without exposing passwords or secrets.
- Use appropriate database indexes.

Create Mongoose models for:

1. AdminUser
2. Tournament
3. Team
4. TournamentEntry
5. TournamentStage
6. Group
7. Match
8. MatchEvent
9. TournamentStanding or another suitable standings representation
10. AuditLog

Use references between related records where appropriate.

Support multiple tournaments in the same database.

A team must be reusable across different tournaments without duplicating the team's identity unnecessarily.

Tournament participation, group assignment, statistics, and qualification must be specific to each tournament.

Do not store every tournament's data inside one giant MongoDB document.

Design the database so that updates to a match, team, or tournament do not require rewriting unrelated records.

7. TOURNAMENT FORMATS
==================================================

Support these tournament formats:

A. LEAGUE FORMAT

Every participating team plays the configured opponents according to the selected scheduling rules.

Support single round-robin and double round-robin competitions.

B. GROUP STAGE FOLLOWED BY KNOCKOUTS

Allow administrators to configure:
- Number of groups
- Number of teams per group
- Group assignments
- Qualification places per group
- Best third-placed teams or other configurable qualification rules
- Knockout seeding rules

Automatically calculate group standings and identify qualified teams.

C. STRAIGHT KNOCKOUT

Create knockout rounds such as:
- Round of 64
- Round of 32
- Round of 16
- Quarter-finals
- Semi-finals
- Final

Support appropriate preliminary rounds when the team count is not a power of two.

D. LEAGUE PHASE FOLLOWED BY KNOCKOUTS

Allow a league phase followed by a knockout phase.

The administrator configures:
- Number of teams
- League-phase fixtures
- Number of teams qualifying
- Qualification positions
- Knockout seeding
- Whether ties are single-leg or two-legged

Do not hard-code the website to a specific competition format.

All competition settings must be configurable.

Use reliable fixture-generation algorithms and validate that the resulting schedule does not accidentally duplicate fixtures or schedule a team against itself.

Allow manual fixture editing after generation.

8. TOURNAMENT STAGE MANAGEMENT
==================================================

This is one of the most important features.

Create a dedicated stage-management system.

Administrators must be able to add, edit, reorder, complete, and manage tournament stages.

Examples:

- League Phase
- Group Stage
- Round of 32
- Round of 16
- Quarter-finals
- Semi-finals
- Third-place Play-off
- Final

Each stage should have:
- Stage name
- Stage type
- Stage order
- Tournament reference
- Stage status
- Participating teams
- Qualification rules
- Match format
- Optional group assignments
- Start and end dates

Stage statuses:

- Upcoming
- In progress
- Completed

When a stage is completed, the administrator can create the next stage.

The system must preserve all previous stages, fixtures, scores, standings, and results.

Visitors must be able to select previous stages to view their information.

Never overwrite the league-phase table when creating the knockout stage.

Each stage must maintain its own records.

Implement two methods of qualifying teams:

1. Automatic qualification based on configured competition rules.
2. Manual qualification where the administrator selects teams.

Before creating a new stage, display a preview of the teams that will qualify.

Require administrator confirmation before committing the new stage.

Validate that teams are eligible and that the same team is not accidentally entered twice in a stage.

For knockout progression, automatically identify winners after a tie is officially completed.

For two-legged ties, calculate the aggregate score.

Do not automatically eliminate teams based on aggregate scores alone when a tie is level and extra time or penalties are required.

Allow the administrator to record extra-time and penalty-shootout results when applicable.

Provide a controlled manual override for exceptional cases, with an audit log explaining the change.

9. LEAGUE STANDINGS
==================================================

Generate a dynamic league table.

Display:

- Position
- Team logo
- Team name
- Matches played
- Wins
- Draws
- Losses
- Goals for
- Goals against
- Goal difference
- Points

Calculate standings from officially completed matches only.

Default points system:
- Win: 3 points
- Draw: 1 point
- Loss: 0 points

Allow administrators to configure the points system before or during a tournament, while warning them that changes may recalculate standings.

Provide configurable tiebreakers.

Possible tiebreakers include:
- Total points
- Goal difference
- Goals scored
- Head-to-head points
- Head-to-head goal difference
- Head-to-head goals scored
- Fair-play points, when configured
- Play-off match, where the tournament rules require it

Do not assume that every tournament uses the same tiebreaker order.

Allow administrators to configure the applicable order.

For group tournaments, calculate each group's standings separately.

Update the standings when:
- A match is completed.
- A completed result is corrected.
- A result is annulled.
- An eligible match is otherwise changed.

Never count an upcoming, postponed, abandoned, or live match as an officially completed result.

Make standings updates consistent and reliable.

Avoid double-counting a match when it is edited or processed more than once.

Use a reliable recalculation strategy so that the database can recover from errors.

==================================================

Support these statuses:

- Scheduled
- Live
- Half-time
- Extra-time
- Penalty shootout
- Full-time
- Postponed

- Away team
- Team logos
- Current score
- Match clock or minute
- Match status
- Scheduled kickoff time
- Match events
- Administrative controls

Allow administrators to:
- Start a match.
- Update the home score.
- Update the away score.
- Set the match minute.
- Pause or update the match clock.
- Mark half-time.
- Resume the second half.
- Start extra time.
- Record penalty-shootout scores.
- Mark full-time.
- Suspend a match.
- Postpone or abandon a match.
- Correct a result.
- Reopen a completed match with appropriate permissions.

The score should update on the public frontend without a page refresh using Socket.IO.

When the match ends:
- Save the official result.
- Recalculate affected standings.
- Update the results list.
- Update qualification calculations when appropriate.
- Advance knockout winners when the tie is fully resolved.
- Notify connected clients of the changes.

Implement safe match-state transitions.

Use server-side validation to prevent unauthorized or invalid state changes.

Support score correction after full-time. If an official result changes, recalculate standings and any dependent tournament progression safely.

For two-legged ties, distinguish individual match scores from aggregate tie scores.

The public website must never trust a score or status supplied directly by a browser without server validation.

21. DATABASE CONSISTENCY AND BUSINESS RULES
==================================================

Where practical, use MongoDB transactions for operations that update multiple related documents.

If transactions are used, document the MongoDB deployment requirements and provide a safe approach for supported MongoDB Atlas deployments.

Never silently replace an existing team in a completed knockout tie.

Use optimistic concurrency control or equivalent safeguards for conflicting administrative updates where appropriate.

Record important changes in the audit log.
